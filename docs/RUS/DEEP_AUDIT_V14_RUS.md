# Глубокий самостоятельный аудит v13 → v14 — 2026-11-12

## Метод

Повторно проверены не только ранее изменённые функции, но и их границы:
путь загрузки LoRA → memory cache → повторная активация, сочетания 1/2/4 LoRA,
TE/U-Net/DYN/LBW/LBWE/кривые/Hires, API authentication и путь package install →
runtime tests → rollback. Старые зелёные тесты не считались достаточными: добавлены
два отрицательных сценария для LoRA file identity.

## Подтверждённый дефект

У LoRA cache `network_file_signature()` до v14 состояла только из mtime и размера.
Такой же по размеру файл, записанный под тем же именем с сохранённым mtime, мог
сохранить ранее загруженные tensors. Это особенно реально при синхронизации модели
из другого каталога или `os.replace`.

v14 сохраняет совместимый первый элемент mtime, но добавляет ctime, dev, inode и
canonical realpath. Загрузка также повторно считывает signature после
`read_state_dict`: изменение в процессе чтения вызывает понятный отказ и повтор
после завершения записи, а не публикацию потенциально смешанного payload.

Новые проверки:

1. Реальная same-size replacement с восстановленным mtime меняет signature.
2. Имитированная смена signature между началом и концом чтения прекращает загрузку.

## Границы вывода

Signature не является криптографическим хешем: экзотическая файловая система может
сохранить все stat-поля при подмене; тогда остаётся явная перезагрузка. Не были
запущены настоящее Gradio, CUDA/WAI, пользовательские LoRA/TI, VRAM/FPS и внешние
extensions. Поэтому v14 подтверждает корректность проверенных CPU-сценариев, но не
выдаёт их за полную GPU-приёмку.
